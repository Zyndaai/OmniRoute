# PostgreSQL persistence and cluster mode

OmniRoute keeps all durable state in one PostgreSQL database. It runs either as one process
(standalone) or as a cluster on one host: one leader and N workers, all on the same database,
coordinated through PostgreSQL or Redis. This page covers what is shared, what each process keeps
for itself, and what an upstream provider sees per account when N processes serve it. The
repository boundary rules are in [`persistence-backend-boundary.md`](persistence-backend-boundary.md);
the schema is in [`postgres-schema.md`](postgres-schema.md).

## Persistence

- PostgreSQL is the only backend. `OMNIROUTE_POSTGRES_URL` points at it, and startup fails when it
  cannot be reached: there is no fallback store (`src/lib/db/core.ts`). Tests use a disposable
  PostgreSQL too (`tests/_setup/isolatePostgres.ts`, one cloned database per test file).
- PostgreSQL migrations live in `src/lib/db/backends/postgres/migrations/` (`0001_init.sql` is the
  squashed baseline). The leader applies them at boot; a worker waits until the database reaches
  its image's migration head.
- The memory engine (FTS5 and sqlite-vec) was removed, so its tables are not in the schema.
- Call-log detail bodies are JSON files under `<DATA_DIR>/call_logs`, not database rows
  (`getCallLogsDir()` in `src/lib/usage/callLogArtifacts.ts`, written by
  `writeCallArtifactAsync` in `callLogArtifactWriter.ts` through a worker thread). Detail reads
  and rotation (`callLogRotation.ts`) need the same files, so every process mounts the same
  `DATA_DIR`.

SQL written for PostgreSQL follows these mappings from the old SQLite constructs:

| SQLite construct                               | PostgreSQL form                                                       |
| ---------------------------------------------- | --------------------------------------------------------------------- |
| `INTEGER PRIMARY KEY AUTOINCREMENT`            | `bigint GENERATED BY DEFAULT AS IDENTITY`                             |
| `lastInsertRowid`                              | `RETURNING`                                                           |
| `INSERT OR REPLACE`                            | `INSERT ... ON CONFLICT ... DO UPDATE SET` with explicit columns      |
| `COLLATE NOCASE` and case-insensitive matching | database collation C; `LOWER()` comparisons or `ILIKE`                |
| `json_extract(col, '$.x')`                     | `safe_jsonb(col)::jsonb ->> 'x'` (`safe_jsonb(text)` in the baseline) |
| `strftime(...)`                                | `to_char` or `date_trunc`                                             |
| Triggers                                       | foreign keys with `ON DELETE CASCADE`, or checks in the repository    |
| `BEGIN IMMEDIATE` mutual exclusion             | `SELECT ... FOR UPDATE`                                               |
| `SQLITE_BUSY` retries                          | retries keyed on PostgreSQL SQLSTATE classes                          |

Two habits matter on PostgreSQL. A read-modify-write of a JSON column (`provider_specific_data`)
must lock the row (`SELECT ... FOR UPDATE`) or merge only its own keys
(`mergeConnectionProviderSpecificData`); writing back a whole object read earlier loses
concurrent updates. And every uncached read is a network round trip, so hot paths read through
`src/lib/db/readCache.ts`.

## Roles

`OMNIROUTE_ROLE` decides the role (`src/lib/cluster/role.ts`):

| Role         | Set by                  | Does                                                                                                                 |
| ------------ | ----------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `standalone` | unset (the default)     | everything in one process; takes the fence so a second process on the same database exits; no bus                    |
| `leader`     | `OMNIROUTE_ROLE=leader` | migrations, background jobs, the dashboard, and the only process that refreshes single-use OAuth tokens; fence + bus |
| `worker`     | `OMNIROUTE_ROLE=worker` | serves requests; no migrations or jobs (`OMNIROUTE_DISABLE_BACKGROUND_SERVICES` is forced on); bus only              |

Cluster mode (leader or worker) refuses to boot without a valid `OMNIROUTE_INSTANCE_ID` and with
`JWT_SECRET` or `API_KEY_SECRET` missing: they come from the shared environment, because a worker
that generated its own JWT secret would reject every leader-issued session.

Leader-only work (`src/server/boot.ts`, gated by the boot plan's `leaderDuties`): migrations and
seeds, the credential-health sweep that refreshes OAuth tokens, the handler for workers' refresh
requests, the proxy health and free-proxy schedulers, the API bridge server, audit-log and
retention cleanup, the cleanup scheduler, quota refreshes, and the optional subsystems.

Deployment: one container runs PM2 (`ecosystem.config.cjs`, fork mode): `leader` on 20128 and
`worker-i` on 20200+i, each with `OMNIROUTE_CLUSTER_SIZE` = workers + 1, next to PostgreSQL and
Redis (`docker-compose.cluster.yml`). Caddy sends the management plane (`/dashboard*`, `/home*`,
`/api/*` except `/api/v1/*`, `/live-ws*`) to the leader only, and inference (`/v1/*`,
`/api/v1/*`) to every process, sticky by `x-session-affinity`. Caddy cannot route by upstream
account (it picks a process before OmniRoute picks an account), so account-level consistency is
the processes' job, below.

## Coordination

Transport (`src/lib/cluster/runtime.ts`): PostgreSQL by default, Redis when `REDIS_URL` is set.
Both fail closed: a leader that can no longer prove it holds the fence exits.

- **Leader fence.** PostgreSQL: a session advisory lock (`pgLeaderFence.ts`). Redis: `SET NX PX`
  on `cluster:leader` with a 30 s lease renewed every 10 s (`leaderFence.ts`). A second leader, or
  a standalone process on a database that already has one, exits with code 1.
- **Bus** (`bus.ts`; PostgreSQL `LISTEN/NOTIFY` in `pgBus.ts`, or Redis pub/sub). Each message
  carries its origin, and a process skips its own. Missed messages are bounded by the cache TTLs,
  and a reconnect runs the resync handlers (`onBusResync`).
  - `cluster:invalidate` scopes:

    | Scope           | Effect on receivers                                               | Source                                  |
    | --------------- | ----------------------------------------------------------------- | --------------------------------------- |
    | `api-keys`      | drop the API-key caches                                           | `src/lib/db/apiKeys.ts`                 |
    | `db-cache`      | invalidate read-cache namespaces (settings, providers, ...) by id | `src/lib/db/readCache.ts`               |
    | `model-catalog` | bump the model-catalog cache version                              | `src/lib/db/readCache.ts`               |
    | `rate-limits`   | re-read one connection's (or all) rate-limit settings from the DB | `open-sse/services/rateLimitManager.ts` |
    | `quota`         | apply a quota entry (newer `fetchedAt` wins) or reload snapshots  | `src/domain/quotaCache.ts`              |

  - `cluster:refresh-request {connectionId, reason}`: a worker that finds an expired or rejected
    token asks the leader to refresh it (`open-sse/services/tokenRefresh/passiveRefresh.ts` →
    `src/lib/cluster/leaderRefresh.ts`), then re-reads the new token from the database.
- **Per-account rate limits** (`open-sse/services/rateLimiter/`). With Redis in a cluster the
  limiter state is shared and exact (`redisSlotState.ts`: Lua on Redis `TIME`, leased concurrency
  slots, fail open). With PostgreSQL only, each process enforces 1/N of each limit
  (`open-sse/services/clusterShare.ts`, N = `OMNIROUTE_CLUSTER_SIZE`), which keeps the average
  rate but lets up to N requests start together.

## What a provider sees per account

The goal is that a provider sees the same client from a cluster as from one process: one machine,
one identity per account.

- **Egress IP and TLS.** Every process in the container leaves through the host's IP (or the
  connection's assigned proxy, chosen from shared cursors) with the same Node, undici and OpenSSL
  stack, so the IP and the TLS/HTTP-2 fingerprint do not change with N.
- **Claude** (`open-sse/executors/claudeIdentity.ts`): `session_id` is
  `uuidV4FromHash(HMAC(API_KEY_SECRET, "claude-session:<UTC day>:<seed>"))`, the same in every
  process and rotating daily. The device id is the persisted `cliUserID` (set at OAuth or token
  import), else `HMAC(API_KEY_SECRET, "claude-device:<connectionId>")`. Without `API_KEY_SECRET`
  (standalone only) both fall back to per-process random values. `account_uuid` falls back to a
  value derived from the access token when none is persisted, so it changes when the token does.
  Test: `tests/unit/cluster-claude-identity.test.ts`.
- **Codex** installation, session and thread ids derive from a persisted seed
  (`open-sse/config/codexIdentity.ts`); the **Antigravity** session id is a hash of the account key
  (`open-sse/services/antigravityIdentity.ts`). Both are identical across processes.
- **User-agent and client version strings** come from env and constants, so they are the same in
  every process of one image.
- **Token refresh** happens on the leader only, so a single-use refresh token is never spent twice.

What N processes do change: up to N × `maxConcurrent` in-flight requests per account, and a few
extra 429s while each process learns a lockout on its own. Pool strategy matters more than N: a
`round-robin` pool changes the egress IP on every request even in one process, so subscription
OAuth accounts should egress direct or through one fixed proxy (`sticky` with a long window if a
pool is assigned).

Judgment, not code: the dominant risk to subscription accounts is volume, not process count.
Anthropic's Claude Code terms describe OAuth as meant for ordinary individual use, and providers
have suspended accounts used through third-party OAuth tools ([`STEALTH_GUIDE.md`](../security/STEALTH_GUIDE.md)).
Extra cluster capacity should land on API-key providers, not raise the per-account rate.

## Egress path

How one upstream request picks its route and identity:

1. The process picks an account with `getProviderCredentials` (`src/sse/services/auth.ts`), which
   respects the shared cooldowns.
2. `safeResolveProxy` (`src/sse/handlers/chatHelpers.ts`) calls `resolveProxyForConnection`
   (`src/lib/db/settings.ts`), which walks the cascade: global switch, per-key switch, API-key
   proxy, account pool, legacy key level, provider pool, combo, legacy provider, no-auth
   providers, global pool, legacy global, auto-select fallback (`PROXY_AUTO_SELECT_ENABLED`, off by
   default), then direct. A dead assigned proxy fails closed (`PROXY_ASSIGNED_UNAVAILABLE`) unless
   `PROXY_FAIL_OPEN` is set. Pools pick `round-robin` (default), `random`, `sticky` or `latency`.
3. The executor runs the call inside `runWithProxyContext` (`open-sse/utils/proxyFetch.ts`), an
   AsyncLocalStorage scope holding the chosen proxy, and builds the provider's headers and body
   identity.
4. The patched `globalThis.fetch` sends it one of four ways: direct through undici (32
   connections per process by default, `OMNIROUTE_PROXY_DISPATCHER_CONNECTIONS`, HTTP/2 allowed);
   through an HTTP or SOCKS proxy (undici `ProxyAgent`, cached per proxy URL); through an edge
   relay (`x-relay-*` headers); or through wreq, which imitates Chrome's TLS handshake, only when
   `ENABLE_TLS_FINGERPRINT=true`. Unproxied requests honour `HTTPS_PROXY`; an assigned proxy wins
   over it.

The connect guard (`open-sse/utils/connectGuardDispatcher.ts`, an SSRF check against DNS
rebinding for user-supplied URLs) and the MITM module (`src/mitm/`, a local TLS-intercepting
proxy for desktop CLIs) are not part of provider identity.

## Rehearsing on a copy of production data

A copy of the production database holds live single-use refresh tokens: one refresh that escapes
from a rehearsal revokes production's token family for that account. A rehearsal on copied data
must run its app containers on a Docker network with `internal: true` and give any capture proxy
no upstream route, so an escaped request fails instead of reaching a provider. `HTTPS_PROXY` alone
is not enough: an assigned proxy, the direct sentinel, bypass hosts and the original fetch all
skip it. Or rehearse on credentials that are not production's (`docker-compose.rehearsal.yml`
expects test provider accounts).
