# Persistence on PostgreSQL with shared state

OmniRoute moves from one SQLite file and one process to one PostgreSQL database shared by N processes: one leader and any number of workers. PostgreSQL is the only production backend. SQLite stays for tests and local development, behind domain repositories, and production runs with no SQLite file. This record follows the boundary in [`persistence-backend-boundary.md`](persistence-backend-boundary.md), reverses the PostgreSQL drop in [`cluster-decisions.md`](cluster-decisions.md), and cites the coupling measured by `scripts/check/db-coupling-inventory.mjs`.

## Decision

- PostgreSQL is the only production backend. SQLite is for tests and local development only.
- Domain repository contracts live in `src/domain/persistence/*.ts`, following the existing `comboRepositories.ts` pattern.
- The SQLite implementations are the current SQL, lifted without changes, into `src/lib/db/repositories/sqlite<X>Repository.ts`. The PostgreSQL implementations go in `postgres<X>Repository.ts`.
- Everything moves to PostgreSQL, including `semantic_cache`, `reasoning_cache` and `request_detail_logs`.
- The memory engine (FTS5 and sqlite-vec, under `src/lib/memory/`) is removed.
- The leader fence and the coordination bus run on Redis. Redis is required and fails closed.
- The PostgreSQL schema starts from one squashed baseline, `src/lib/db/backends/postgres/migrations/0001_baseline.sql`, taken from today's schema. Every later schema change ships as a SQLite migration and a PostgreSQL migration, and a test enforces that each pair exists.

## Table placement

All tables move to PostgreSQL. The memory engine is removed, so the PostgreSQL baseline omits its tables:

- `memories` (migration 015)
- `memory_fts`, an FTS5 virtual table (migrations 022 and 023)
- `memory_vec_meta` (migration 083)
- `vec_memories`, a sqlite-vec `vec0` table. It is created at runtime by `src/lib/memory/vectorStore.ts`, not by a migration, so a schema diff against migrations alone will miss it.

The inventory counts 140 tables from `CREATE TABLE` statements in `src/lib/db/migrations/*.sql` and `src/lib/db/core.ts`.

## Construct mapping

| SQLite construct                                | PostgreSQL form                                                                         |
| ----------------------------------------------- | --------------------------------------------------------------------------------------- |
| `INTEGER PRIMARY KEY AUTOINCREMENT`             | `bigint GENERATED BY DEFAULT AS IDENTITY`                                               |
| `lastInsertRowid`                               | `RETURNING`                                                                             |
| `INSERT OR REPLACE`                             | `INSERT ... ON CONFLICT ... DO UPDATE SET` with explicit columns                        |
| Timestamps                                      | text, unchanged                                                                         |
| Booleans                                        | integer 0/1, unchanged                                                                  |
| `COLLATE NOCASE` and case-insensitive matching  | database collation C; `LOWER()` comparisons or `ILIKE`                                  |
| `json_extract(col, '$.x')`                      | `safe_jsonb(col)::jsonb ->> 'x'`, using a `safe_jsonb(text)` function in the baseline   |
| `strftime(...)`                                 | `to_char` or `date_trunc`                                                               |
| Triggers from migration 126                     | foreign keys with `ON DELETE CASCADE`                                                   |
| `BEGIN IMMEDIATE` mutual exclusion              | `SELECT ... FOR UPDATE`                                                                 |
| `SQLITE_BUSY` retries                           | retries keyed on PostgreSQL SQLSTATE classes                                            |

Each domain must still state its observable semantics (timestamps, NULL ordering, pagination tie-breakers, affected-row counts) as [`persistence-backend-boundary.md`](persistence-backend-boundary.md) requires. This table only maps constructs.

## Environment

- `OMNIROUTE_DATABASE_DRIVER`: `sqlite` (default) or `postgres`.
- `OMNIROUTE_POSTGRES_URL`: the PostgreSQL connection. When the driver is `postgres` and the database cannot be reached, startup fails. It never falls back to SQLite.
- `OMNIROUTE_ROLE`: `leader` or `worker`. Required; there is no default.
- `REDIS_URL`: the existing variable, now required and fail-closed.

## Process roles and coordination

The leader runs all background jobs and all migrations. It is the only process that refreshes rotating (single-use) OAuth tokens, so two processes never spend the same refresh token. Workers serve traffic and do not run jobs. Redis holds the leader fence (`SET NX PX`) and a pub/sub bus for cache invalidation and refresh requests.

## Call-log artifacts

Call-log detail bodies are written as one JSON file per request, not in the database. The directory is configurable.

- `getCallLogsDir()` (`src/lib/usage/callLogArtifacts.ts:23`) returns `<resolved data dir>/call_logs`, or `null` on cloud.
- The data dir comes from `resolveWritableDataDir()` (`src/lib/dataPaths.ts:130`), which reads the `DATA_DIR` environment variable through `resolveDataDir()` (`src/lib/dataPaths.ts:64`, variable at line 67). Without `DATA_DIR` it falls back to the per-user default.
- The write path is `publishCallLogDetail` (`src/lib/usage/callLogs.ts:802`) calling `writeCallArtifactAsync` (`src/lib/usage/callLogArtifactWriter.ts:224`). The writer hands the job to a worker thread (`src/lib/usage/callLogArtifactWorker.ts`), and the parent passes its resolved `DATA_DIR` into that worker.
- Reads also use the directory. The detail lookup in `src/lib/usage/callLogs.ts:1014` runs in whichever process serves the dashboard.

Each artifact is a `.json` file under a date folder. Plan: mount one shared volume at `DATA_DIR` in every container. Workers need the files for detail reads, and rotation and cleanup (`src/lib/usage/callLogRotation.ts`) must see the same files the writers produced, so every process needs the same directory.

## Inventory

Run from the repository root:

```sh
node scripts/check/db-coupling-inventory.mjs > coupling.md
```

The script is a line- and regex-based scan of `src/` and `open-sse/`, test files excluded. It over-counts a table name that is also a variable, and it under-counts references that have no SQL keyword on the same line, such as the table list in `src/lib/db/cleanup.ts:882`. Headline counts on 2026-11-16:

- 140 tables.
- 5,855 source files scanned.
- 235 files contain `.prepare(` (1,523 occurrences).
- 208 files import `getDbInstance`, all from a `core` module. 148 of them are inside `src/lib/db/`. The other 60 are outside it: 7 in `open-sse/` (for example `open-sse/mcp-server/server.ts`, which imports `../../src/lib/db/core.ts`) and 53 elsewhere in `src/`.
- 59 lines contain `JOIN`, in 30 files.

`open-sse/` reaching into `src/lib/db/core.ts` means the open-sse package cannot be moved to a PostgreSQL-only build without first removing those imports. That is a follow-up for the repository stage.
